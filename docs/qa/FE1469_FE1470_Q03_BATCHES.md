## 一、输入绑定（复审 §一.1 的补正）

要求是「引用既有冻结原件和哈希即可，不必重新建一套台账」，所以本批**不新建快照文件**，只做三件事：

| 项 | 取值 | 来源 |
|---|---|---|
| 清单快照 | `cee1afdabf232f0f8ddaa4f49bd6f33fbe8779b0a963c53e2fc5c406bd4535aa` | `scripts/iqc/runs/inventory_manifest_r2.json` 的 `snapshot_sha256` |
| 同一快照的历史运行 | `run_id FE1460-eb662b5c` | `scripts/iqc/runs/findings_fe1460_225.jsonl` |
| 逐题审计哈希 | 26 条各自 `audit_input_sha256` | manifest 已登记值，**引用** |
| 哈希口径 | `scripts/iqc/common.py::audit_input_sha`（九域规范化） | 与 `scan.py` 同一份代码 |

**每个结论都带两个哈希**：manifest 里的引用值 + 现场重算值。两者不等即 `drift=true`，脚本以退出码 1 失败——意思是「这道题在快照后被改过，旧结论作废」，而不是「沿用旧结论并打个警告」。

**求解器版本的处理**（复审 §四 已纠正）：上一版 `provenance.solver_version.script`
只写了 `rt1469/q03_number_input.py`，而实际入口是 `rt1470/q03_batch2.py`——**这是错的**。
现在分三项列明，**缺一项都不足以定位生成者**：

| 字段 | 第二批的取值 | 作用 |
|---|---|---|
| `entry_script` | `scripts/iqc/rt1470/q03_batch2.py` | 真正跑起来的入口 |
| `entry_sha256` | 运行时计算 | 反映**实际执行的字节**；工作区有未提交改动时以它为准 |
| `shared_modules[]` | `rt1469/q03_number_input.py`（`bind_inputs`/`judge_binding`）、`common.py`（`audit_input_sha`） | 被 import 复用、参与绑定计算的模块，各带 sha256 与 role |
| `git_commit` | 运行时 `git rev-parse HEAD` | 报告生成时所在提交 |

用户原话：「**改动在 diff 里看得见**」不等于「离线报告已说明自己由哪个版本生成」。
所以这里既有 commit，也有文件哈希——两者互补，不是重复。

**结果链条**（工件 `provenance.result_chain` 同文）：

```
当前工作清单中的 RVID
  → 被复用的冻结输入 inventory_manifest_r2.json（snapshot_sha256 cee1afda…）
  → 逐题 audit_input_sha256（引用值 == 现场重算值）
  → 本次核验结果 verdict
```

`cee1afda…`（第二批引用的清单快照）与 `79f90852…`（224 条清单引用的）**不是矛盾**：
后者是早一轮清单的哈希，前者是当前 manifest 的 `snapshot_sha256`。
两个值都保留在工件里，链条才能从「当前清单」走到「冻结输入」再走到「结果」；
抹掉任何一个，都无法复现这条路径。

**实测**：26 条 drift 全为 0。

## 三、负对照的效力边界（复审 §三 要求分开）

> 「故意改错存储答案，能够验证比较器发现不一致；**不能单靠它证明题干解析本身正确**。」

所以负对照分三组，**各自证明不同的事**：

| 组 | 做法 | 证明了什么 | **没有**证明什么 |
|---|---|---|---|
| **A** 改存储答案（7 条） | 把 stated 换成错值 | 比较器不是永真 | 题干读对了 |
| **B** 改配置独立事实（10 条） | 模型吃配置，改 `initial_count`/`operands`/`object` 等 | 推导**真的依赖**题面数值 | 所有类型的题都覆盖了 |
| **C** 必要条件不成立（3 条） | 尺子两端颠倒、单框放不下 13、减法出负数 | 前提不成立时会**受控拒绝**，不硬算 | 拒绝判据本身完备 |

每组都带**反向确认**，防止「检出」是假的：

- A 组：换回原值必须 MATCH（若比较器恒返回不等，A 组会全过但毫无意义）
- B 组：同一模型吃**真实配置**必须复现该题手推值（10/10 一致）
- C 组：同一函数在合法输入下必须给出正确答案（否则"拒绝"可能只是坏函数）

### B 组的一处返工（如实记录）

B 组第一版我写成「比较 `6+4` 与 `5+4` 两个常量表达式的结果是否不同」——**那是同义反复**，改不改代码都会通过。它测的是「算术库会不会算加法」，不是「推导是否读了题面」。

改成模型函数 `model(config) -> int` 之后才有意义：

```
model_ten_frame({"initial_count": 6, "add_count": 4, "max_frames": 1})  → 10
model_ten_frame({"initial_count": 5, "add_count": 4, "max_frames": 1})  → 9
```

第二行必须等于 9、且不等于第一行。这样一旦有人把 `initial_count` 从推导里去掉（比如硬编码 +4），立刻检出。

**B2 还暴露过一次我自己的取样错误**：我本想测「`add_count` 3→8 后应为 11」，但 3+8=11 在 `max_frames=1` 下超出十格框容量，模型正确地抛了错——**是我选的测试数据违反前提，不是模型坏了**。改测 `initial_count 3→2` 后通过。这条记在这里，因为它正好演示了 C 组判据是真的在起作用。

## 四、Q05 候选（复审 §二.4 后的重写：逐题具体化）

### 4.1 上一版错在哪

用户原话是最直接的诊断：

> 「`requirement` 实际上全部是同一句通用说明……
>  **Q05 的免责声明不能只放在 `not_concluded` 字段里，其他字段仍在直接诊断孩子。**」

两个问题各自独立：

1. **套模板**：22 条共用一句「需补充可观测证据……仅有 `code==pattern` 不足以证明区分力」。
   这句话本身没错，但它对每一题说的都是同一件事，等于没回答「**这一题**要看哪个可观察量」。
2. **免责放错位置**：把「不主张」写进 `not_concluded`，同时 `applicable_conditions` 里
   仍写着「答 24 说明把减号当加号」这类直接诊断——**等于一边免责一边定罪**。

### 4.2 现在的三字段结构

每条候选必须回答三个问题，且**只能引用本项目真实存在的提交字段**：

| 字段 | 回答什么 | 反例（不许写） |

| `competing_explanations` | 同一个痕迹还能由哪些别的解释产生 | 「该错法可被唯一识别」 |
| `neutral_feedback` | 要反馈的话怎么说才不断言动机 | 「说明孩子没有掌握退位」 |

字段出处全部可查（工件注释里逐条列了函数名）：

### 4.3 三个值得单独讲的例子

**① `1b3c314e`（90−27）：两条错法能被字段分开，这是本轮最有价值的一条**

用户给定的「错误步骤 → 错误结果」表，恰好对应两组不同的提交形态：

| 错误步骤 | 错误结果 | `result_digits` | `carries` 个位标记 |
|---|---:|---|---:|
| 每位都拿大数字减小数字（十位 9−2、个位 7−0） | 77 | 十=7, 个=7 | **0** |
| 个位借十后算 10−7，十位没扣借出的 1 | 73 | 十=7, 个=3 | **1** |

**73 与 77 的差别不在答案数字，在 `carries`**——孩子到底点没点那个借位开关，
是可直接读出的。这是本批唯一能「结构上分开两种错法」的例子，其余题只能到「终值不同」。

`39ce2243`（54−27）同理：33（逐位大减小，carries=0）vs 37（借了未扣账，carries=1）。

**② `ruler` 4 题：结构码是真的**

`evaluateMeasurement` 会给出专属错误码 `from_zero_reading`——它要求
标记恰好落在 `{0, right}`。这不是推测，是代码里的精确靶：

```ts
function isFromZero(state, config) {
  const lo = Math.min(...state.marks), hi = Math.max(...state.marks);
  return lo === 0 && hi === config.right;
}
```

所以「从零读」在本 renderer 上是**可判定的**，比 `calc` 这种泛化码强得多。
但仍不主张「孩子一定这么想」：`span=7` 也可能只是量偏了，
只是 `error` 码为 `from_zero_reading` 时排除了「量偏」这一类。

**③ `object-counter` 5 题：候选在现有交互下不可观测（存量缺陷）**

见 5.5。简单说：`initialObjectCounterV2State(config.groups)` 让页面一打开就是正确答案，
任何错答都要孩子主动点减号。所以这 5 题的 `observable_evidence` 如实写成
「total=4 只能来自孩子点了 3 次减号——那更可能是误触」，**而不是编一个观察点**。

### 4.6 撤回：不再要求「同一题两个错法不能共用证据」

上一版门禁（T7d）有一条硬规则：同一 `renderer` 内出现相同 `observable` 文本即判 FAIL，
理由是「又套模板」。**该规则现已撤销**，理由有两条：

1. **两题的可观察字段真的一样时，描述相同才是如实登记。**
   例如 `eaa828b3` 与 `cfc971b4` 同为「8 与 5 两组物件比较」，`count` 都写死、
   都只有 `items[].x` 与 `aligned` 会变——把两段文案改得不一样，
   不会增加任何区分力，只会让描述偏离事实。
2. **它属于「为了过门禁而改写文字」的那一类要求**，与本轮反复确认的原则冲突。

因此本批口径改为：

- **22 条候选记录 / 20 个不同签名是正确的、不需要凑成 22/22 唯一。**
  同一题的两个错法码复用同一组三字段，是登记事实，不是缺陷。

##### DEF-D1：存在目标值提示风险，不等于「白送分」

`bars[].max == answer` 是可确认的配置事实，`BarModel.tsx` 的滑杆
`max={Math.max(min + 1, barMax)}` 使最右端恰为答案值。所以孩子**可以**不推理
就把未知条摆到正确长度——这使表征作为「是否理解比较关系」的证据区分力很弱。

但**不能写成「只拖到底即满分」**：V1 仍有独立的数字答案输入框
（`TaskRenderer.tsx::ManipulativeRenderer` 同时渲染 `AnswerComposer`），
而判分读的是 `response.answer`（`learning.py` 用 `content.answer` 与
`response.answer` 比较），`representation` 不参与判分。
更准确的说法是**表征层的答案泄露风险**。

##### DEF-D2：线索，不是「物理摆不出」（**本节为撤回重写**）

上一版的推论链是「最终答案 > 所有上限 ⇒ 答案摆不出 ⇒ 永远拿不到分」。
第一步的前提是「未知条必须表示最终合计」，而**这个前提从未核验**。

三题都是「先求另一个人的数量，再求两人合计」的两步题，未知条完全可以表示
**另一个人的数量**：

| RVID | 两个人数值 | 两根比较条可表示 | 最终答案 | 每根条上限 |
|---|---|---|---:|---:|
| `421ede36` | 小青 11，小雨 11−4=7 | 11 与 7 | 18 | 15 |
| `6e5395f0` | 小明 9，小红 9+3=12 | 9 与 12 | 21 | 12 |
| `8981fbcc` | 小兰 8，小杰 8+3=11 | 8 与 11 | 19 | 11 |

**三组「个人数量」都在对应滑杆范围内。** 也就是说，「不可达」的结论建立在
一个未成立的前提上。

`detect_unreachable()` 的局限（已写入工件 `detector_limits`）：

1. **不读条的角色语义**——不知道哪根条代表哪个量，也不知道题目是否要求
   单独展示合计；
2. **取 `max(所有上限)` 而非答案条上限，会漏报**——反例：答案条上限 5、
   另一无关条上限 100、答案 10，该函数取最大 100 后判定「可达」，
   实际答案条摆不出 10。

所以它是「**最终数值超过显示上限**」的**线索检测器**，不是任务可完成性判定器。

##### DEF-D3：没有增减 ≠ 不能一一对应

##### DEF-D4：没有**期望跳步序列**，不是「不记录跳步」

| 问题 | 答案 |

| 有没有记录 | **有**（`jumps` 数组；`[7,7,7]` 与 `[21]` 是不同的记录） |

## 八、审计器自身的失效（2026-10-21 复审实测，已修）

这一节记的是**工具**的错，不是内容的错。写在这里是因为它比任何一条内容
发现都重要：门禁曾经是空转的，而它给出的绿灯曾被当作可信度依据。

### 8.1 实测复现

在隔离副本上对 `test_batch3_contract.py` 做了四种篡改，上一版门禁的表现：

| 篡改 | 上一版门禁 | 应当 |
|---|---|---|
| `independent_eval()` 改成恒返回 0 | **PASS** | FAIL |
| `match` 改成恒 `True` | **PASS** | FAIL |
| 删除 `docs/qa/FE1469_FE1470_Q03_BATCHES.md` | **PASS** | FAIL |
| 删除冻结输入快照 | （当时无此文件） | FAIL |

原因有三：

1. **门禁没有执行 29 题的数学核验**——它只检查枚举、关键词、集合和文档数字，
   从没真正算过一道题，所以「算错了」与「没算」都看不出来；
2. **`if os.path.exists(...)` 把整段检查包住了**——缺文件时静默跳过并输出全 PASS，
   即「缺了验证对象却报通过」；
3. 文档存在性检查只验「有没有这段文字」，验不了「这段文字对不对」。

**结论：结构自洽 ≠ 内容正确。** 一个只检查「自己的常量互相不矛盾」的门禁，
在数学核验整条链路坏掉时依然亮绿灯——这比没有门禁更危险，因为它制造了
虚假的可信度。

### 8.2 修法：离线回放层（T12）+ 缺失即失败

新增 `scripts/iqc/rt1471/batch3_frozen_inputs.json`，冻结 29 题的
`answer` / `error_models` / `ui_schema`（运行时原值）+ `evaluate()` 在其上的

| T12f 把 `independent_eval` 替换为恒 0 后，须 ≥25 题变 `MISMATCH` | 回放层自己是否依赖核验路径 |

**`estimation-canvas` 的一个方法要点**：`target` / `expected` 与 `answer` 同值，
按前批口径属**答案副本**，不能作独立推导依据。本批的 `computed` 只用
`actual` 与 `reference` 求最近整十数，未读 `target`/`expected`。

**口径更正（本次核对代码后修订上一版措辞）**：`tolerance` **不是判分容差**。
`estimate === config.expected` 才 PASS，`tolerance` 只决定 FAIL 分支的
`close` 反馈粒度（「差一点点」vs「差很多」）；后端 `_judge()` 同样是严格相等。
所以本类题不存在「容差内多解」。上一版把 `numeric_tolerance` 理解成
「按可接受集合判定」是推得过远——并集工件 `solve_path_note` 早有更正，
本批以代码为准，不再沿用旧说法。

**`estimation-canvas` 的表达式约束**：`independent_eval()` 的白名单只含算术节点，
`round()` 是 `Call` 节点会被拒绝。改用纯算术
`((actual + ref//2) // ref) * ref`，并对 12 个用例做过自检
（18→20、47→50、31→30、24→20、25→30、26→30、5→10 等全部正确，
其中 20→20、10→10 验证了整十数不被上抬）。

#### 10.4.1 `EVIDENCE_DECLARED_BUT_NOT_ENFORCED` 的准确含义

18 题（= 20 − 2 题 `legacy:direct`，后者没有 `ui_schema` 过程字段）

```python
pc = get_process_constraint(rv.ui_schema if rv else None)
pv = process_validate(pc, response) if pc else None    # ← 为 None 就整段跳过
correct = _judge(expected, user_answer)                # ← 只比最终答案
```

是否给这 20 题加 `process_constraint` 是**产品决策**——加了就改变既有判分行为
（从"只看最终答案"变成"过程不对也判错"），会影响已发布题目。

#### 10.7.1 一次真实的判据错误（记账，不是"一切顺利"）

第 16 项首次运行，20 题**全部报**「stem_sha256 与现场重算不符」。
追查结果是**判据写错了，不是数据错**：冻结侧 `_sha()` 用的是 canonical JSON
（`json.dumps(obj, ensure_ascii=False, sort_keys=True, separators=(",",":"))`），
对字符串会带上引号；我第一版写成 `sha256(stem.encode())`，裸编码。

修法是让核对侧使用与冻结侧**同一个函数**：

```python
def canon_sha256(obj):
    raw = json.dumps(obj, ensure_ascii=False, sort_keys=True,
                     separators=(",", ":")).encode("utf-8")
    return hashlib.sha256(raw).hexdigest()
```

同类第二处：观察项我按 `detail` 字段判"有没有解释"，实际字段是
`severity` / `why` / `evidence` / `consequence` / `not_concluded`——比
`detail` 更全，于是 33 条全部误报。

**这两处都是"判据错 → 误拦"**，即 §8.3 记过的第二类失效。
如果当时选择"放宽判据让它通过"，就会把真缺陷一起放过；
正确做法是**先确认数据对不对，再改判据**——两处都做到了。

### 11.4 本批新增维度一：题面可完成性（**发现 1 道实质缺陷**）

`construct_constraint` 含 `geometry_constraint`（shape-canvas），
存在「答案算得出、但界面上画不出」的可能。故本批单列一条维度。

判定依据是**组件源码事实，不是推断**：

- `parseShapeCanvasConfig()` 只读 `grid` / `target_area` / `target_shape`，
  **`base` 与 `height` 完全不被读取**；
- `applyAddPoint()` 用 `0 <= x < grid` 约束钉位，故坐标系是 `grid` 个点；
- `ShapeCanvasV2.tsx:140` `span = (grid - 1) * CELL`——**渲染跨度是 `grid-1` 格**；
- 第 189 行 `Array.from({length: config.grid})` 渲染 `grid×grid` 个钉位。

即 **`grid` 是钉位数，不是格数**。题面写「5×5 方格纸」时孩子看到的是 4×4 格。

逐题判定后：

| RVID | 题面要求 | `grid` | 组件跨度 | 面积可达 | 结论 |
|---|---|---:|---:|---|---|
| `1d5fab4e` | 底边2×高3 = 6 | 5 | 4 | 是 | FEASIBLE |
| `73c7e8c0` | 底边3×高3 = 9 | 5 | 4 | 是 | FEASIBLE |
| **`8b41e648`** | **长5×宽2 = 10** | **5** | **4** | **否** | **INFEASIBLE_ON_COMPONENT** |
| `a1b71f95` | 底边3×高4 = 12 | 5 | 4 | 是 | FEASIBLE |
| `b38f8898` | 长4×宽2 = 8 | 5 | 4 | 是 | FEASIBLE |

`8b41e648`（V14-P0-102）有两个事实**同时成立**：

1. **题面自洽**：5×5 方格纸画长 5 格的长方形，在真实方格纸上完全合理；
2. **组件做不到**：板上只有 5 个钉位、跨度 4 格，长 5 格画不出来。

穷举 5×5 全部钉位组合后，面积 10 只有 **2 组顶点集合**能通过
`evaluateShapeCanvas`（4 顶点 + 4 直角 + 面积 10），且都是**倾斜正方形**：

```
((0,1),(1,4),(4,3),(3,0))   边长 √10、四个直角、面积 10
((0,3),(1,0),(4,1),(3,4))   同上（镜像）
```

于是这道题同时存在「画不出正解」与「画错形状却能判对」两种情况。
轴对齐的 5×2 需要横跨 5 格（6 个钉位），在 `grid=5` 上**不可能**。

**范围核查（本批已做，防外推）**：全量 published 的 shape-canvas 共 **9 题**，
逐题穷举后**仅此题不可达**，其余 8 题全部 `fits=True`。故这是**单题缺陷**，
不是 renderer 系统性问题。这个结论已固化为自证断言：不可完成集合必须
精确等于 `['8b41e648']`——**不能要求「全部 FEASIBLE」**，那等于逼检测器
对真实缺陷说假话（项目硬规则：门禁不得逼内容说错话）。

四禁仍然遵守：没有改 `grid`、没有改题目尺寸、没有改答案、没有改 Published。
修法（改 `grid` 语义为格数、或把题目改成跨度内尺寸）属产品决策。

### 11.6 独立性的第三种形态：编码常量 ≠ 抄 config

`construct_constraint` 的答案不是「算出来的一个数」，而是
**「构造结果被编码成的一个数」**：

| renderer | 构造动作 | 编码方式 | 该题实例 |
|---|---|---|---|
| sorting-board | 按数值排序 | 排好序拼成多位数 | `[4,9,1,6]` 升序 → `1469` |
| place-value | 按位名摆牌 | 按位权拼数 | 十位5/个位8 → `58` |
| pattern-board | 补空格 | 空格 token 拼接 | 补 4、2 → `42` |
| shape-canvas | 画矩形 | 边长之积 | 2×3 → `6` |

这带来一个前五批不存在的问题：**位权 10 / 100 / 1000 不出现在题干里**。
用第五批的判据（`expr` 数字必须 ⊆ 题干数字）会把它们全部判成「疑似抄 config」。

本批的处理：**不据此判「不独立」，但必须逐条登记**。

```
20/20 题的 expr 数字或来自题干、或已显式登记为 encoding_constants
未解释的题干外数字：无
分布：进位权 17 条 / 个位位权=1（`d * 1` 句式产物）7 条
```

判据的两个自我修正（都记下来，因为都是我自己先写错了）：

1. 首版把 `* 1` 里的 `1` 也报成 `UNCLASSIFIED`，7 道题各一条，

2. 首版对 `d * 1` 的处理放在分诊表之外，导致门禁若检查「无 UNCLASSIFIED」
   会误报 7 条。修正后 `purpose` 字段区分三类：题干内 / 进位权 / 个位位权。

### 11.7 本批的自证：两次「变异无效 ≠ 检测器失效」

第六批核验器 `--selftest` 首轮未通过，两次都是**变异构造错了**：

| 现象 | 真因 | 修法 |
|---|---|---|
| 四类题全报「题干数字变异后 `computed` 未变」 | 变异打偏了：place-value 改的是「位值卡片[5,8]」里的 5（卡片池），而推导用的是「十位是5」；shape-canvas 改的是「5×5方格纸」里的 5（纸张尺寸），不是边长；sorting-board 改的是「桌上有4张数字卡」里的 4（卡数量），不是卡片值 | 改为**逐位逐个数字试**，只要有一处能让 `computed` 变化即证明推导在读题面 |

后果是「config↔题面不一致」这条判据**只在两者一致时**才跑得动，
等于把该判据做成空转。已改为登记 `INCONSISTENT` 并跳过该子检查。

### 12.7 第二轮复核：H3 的语义错误（验收方指出，**最实质的一条**）

#### 12.7.1 我错在哪

初版 H3 断言：

```js
expect(String(body.response.answer))
  .not.toBe(String(unknownBar.value));   // ← 把「合计 ≠ 单条」当作半成品证据
```

**这是把正确的数学关系误判成异常。** 两根条分别表示两个人的数量，
合计**本来就不等于任一加数**——该断言恒真、零信息量，不可能检出任何缺陷。

更糟的是：初版在 H3 之后**直接提交**，没有恢复正确未知量。
第一题（11/7，合计 18，上限 15）实际提交的未知条是 **15**——
既不是正确的 7，也不是合计 18，是个无意义值。而测试却 PASS。

#### 12.7.2 一个极易踩的巧合

| 题 | 已知 | 正确未知量 | 合计 | 未知条上限 |
|---|---|---|---|---|
| d2-1 | 11 | 7 | 18 | 15 |
| d2-2 | 9 | **12** | 21 | **12** |
| d2-3 | 8 | **11** | 19 | **11** |

**d2-2 的 12、d2-3 的 11 既是正确未知量、又恰好等于滑条上限。**
所以「设为合计 → 被夹到上限」停下来的值，在第二、三题上**正好就是正确答案**。
单看这两题会得出「半成品也停在正确值」的荒谬结论。**只有 d2-1 暴露了真实差异**
（停在 15，正确是 7）。这解释了为什么这个问题容易被漏掉。

#### 12.7.3 修正后的断言结构

| 用例 | 断言内容 | 性质 |

#### 12.7.4 H4b 的性质表述已纠正

### 13.2 为什么必须换核验方法：第六批规则在本批会**静默算错**

本批 35 题是同族另一批题，写法与第六批那 20 题不同。用第六批规则现场探针实测：

| renderer | n | 命中 | **算错** | 抽不到 |
|---|---:|---:|---:|---:|
| array-board | 7 | 7 | 0 | 0 |
| estimation-canvas | 1 | 0 | 0 | 1 |
| money-board | 6 | 4 | **1** | 1 |
| pattern-board | 6 | 3 | 0 | 3 |
| place-value | 4 | 2 | 0 | 2 |
| shape-canvas | 4 | 3 | 0 | 1 |
| sorting-board | 7 | 6 | 0 | 1 |

「抽不到」是响的（rc=2 能拦住），**「算错」是哑的**：

> `8a658f5e` 题面写「一支笔标价10角，一块橡皮标价5角」，
> 第六批 `money-board` 规则靠「**另一件**」三字判断两件相加。
> 这句没有那三个字 → 走单件分支只取 10，**真值 15**。
> 不报错、不崩溃，静默产出错值，随后被判成 `MISMATCH` ——
> 看起来像「题库答案错了」，实际是**核验器读错了题**。

这是本批方法学的核心分界：

| 现象 | 真实原因 | 正确处置 |
|---|---|---|
| 抽不到 | 规则不足 | **rc=2**（工件/工具问题），不是核验失败 |
| 抽错（静默） | 规则不足以区分变体 | 同上，但**必须先被发现**——靠「每题必须恰好命中一个登记模板」 |
| 结论不成立 | 推导值 ≠ 存储答案 | **rc=1** |

#### 13.2.1 题面模板显式登记（`STEM_TEMPLATES`）

16 个模板，每题**必须恰好命中一个**：命中 0 个或 >1 个都 rc=2。

```
money 3 / place-value 3 / array 1 / shape 3 / sorting 2 / pattern 4 / estimation 1
```

**歧义不是「选一个更像的」，而是「规则不足，需人工补模板」。** 这条判据在本批
真的触发过一次：`pattern_named_codes` 与 `pattern_named_codes_two_rounds`
共用同一抽取器 → 报「命中 2 个模板（歧义）」，处置是**合并为一个模板**并
修正抽取器（以「……」为终止锚点、把 `，` 也当分隔符），不是放宽判据。

#### 13.3.1 三类非 MATCH 为什么不能并成「大概没问题」

**`STEM_GIVEN_ANSWER_AGREES`（2 题）**：`46701fae` 题面写「组成 352」、
`853ef450` 题面写「面积=6」。题面**就是答案**，于是「独立推导出答案」这件事
根本不存在。记 MATCH 会把「抄题面」说成「复算确认」。

**`UNVERIFIABLE_FROM_STEM`（1 题，`cd7f008d`）**：`actual=38`、`expected=40`
**都不在题面**（题面只给参照「这一摞是 10 本」和定性比较「多得多」）。
用 config 算 config 是循环论证。故记不可核，**不并入 MATCH 覆盖率**。

#### 13.3.2 显式拒绝「按容差判 MATCH」这条捷径

若把 3 道非 MATCH **一律**按容差/宽松口径算成 MATCH，本批会变成
**35 MATCH / 0 非 MATCH**——「全部复算确认」，一个缺口都不剩。

但这个换算对三题里**只有一题**（估算题）勉强谈得上，另两题与容差无关：

| 题 | verdict | 容差是否适用 |
|---|---|---|
| `cd7f008d` estimation-canvas | `UNVERIFIABLE_FROM_STEM` | 形式上适用，但见下 |
| `46701fae` place-value | `STEM_GIVEN_ANSWER_AGREES` | **不适用**（`place-value` 无 tolerance） |
| `853ef450` shape-canvas | `STEM_GIVEN_ANSWER_AGREES` | **不适用**（同上） |

所以「按容差判」连技术上都只覆盖 1 题，而这一题也判不过去——
后端根本不认容差：

```python
# apps/learning-api/app/services/learning.py:1116-1120
def _judge(expected, user_answer) -> bool:
    return float(expected) == float(user_answer)      # 严格相等
```

```ts
// estimationCanvasV2.ts:114   PASS 判据
e === config.expected
// :119   tolerance 只用于算 close（诊断粒度），不参与 PASS
close: Math.abs(e - config.expected) <= config.tolerance
```

**容差不参与 PASS**，所以按容差判 MATCH 会与后端实际行为不符。这是
「两个不同判据不能强行合并」在本题上的具体体现。

> 靠通读发现不了，是拿产物逐题重算才暴露的。

### 13.4 本批的 `encoding_constants`：常量声明从人工分诊变成机器可核

本批在 `derivation` 里逐题显式写下「哪个数是常量、为什么」：
`[{value: 10, purpose: "进位权（十进制位值编码规则）"}, ...]`。

| 范围 | 有声明常量的题 | 常量条数 | 分布（1 / 10 / 100 / 1000） |
|---|---:|---:|---|
| **仅第七批** | 19 / 35 | **42** | 11 / 16 / 8 / 7 |
| 仅第六批 | 11 / 20 | 24 | 7 / 11 / 4 / 2 |
| 六 + 七批合计 | **30 / 55** | **66** | 18 / 27 / 12 / 9 |

> 两组数容易混：**第七批单批是 42 条，六、七批合计是 66 条**。
> 此处刻意分三行列出（单批 / 单批 / 合计），不要只记一个总数——
> 项目已有先例：把两个不同分母的数强行相等，产生了四条假结论。

本批 19 题含题干外数字，**全部被声明常量覆盖**（`check_structured()` 实测 0 违规）。

这让「独立性复核」的 A 段判据首次可以**不用人工分诊**：

| 判据 | 内容 | 为什么需要它 |
|---|---|---|
| ① | 有题干外数字 → 必须声明常量 | 否则就是「抄 config 不说明」 |
| ② | 题干外数字 ⊆ 已声明常量 | 声明必须真的覆盖 |
| ③ | **已声明常量 ⊆ 该答案的十进制位权集合** | 只做 ② 的话，把答案本身写成常量即可通过 |
| ④ | `purpose` 非空且不是 `UNCLASSIFIED` | 声明不能是占位符 |
| ⑤ | 答案本身不得被声明为常量 | 防止「expr 里出现答案 → 声称它是常量」 |

**③ 是这套判据的关键**：常量必须落在 `{1,10,100,...}` 且按 `computed` 位数算出。
编造的常量（如给答案 352 配常量 7）过不去。

### 13.9 `check_progress.py` 与 `check_independence.py` 的同步改动

#### 13.9.1 `check_progress.py`：补上从未有过的自证

全量重算**，不再靠「记得再加一个常量」——这是同一类错误的第三次复现（95 题时

不声称生产题里发生过这种情况，也不写进任何产物或结论。**

### 13.12 真实库输入绑定核对（2026-10-26 补做）

13.1–13.11 的结论全部来自**冻结清单里的题面文本**。这留下一个此前未闭合的面：
如果冻结之后线上的题干、UI 契约或答案被改过，核验会拿**旧题面**推导、再用**旧答案**
比对，全链自洽却与线上题无关——那种「账实相符」是假的。

补做的办法是连真实库核对三列是否与冻结清单同版：

```
answer drift = 0 / 35
stem   drift = 0 / 35
ui     drift = 0 / 35
```

三列都零漂移，说明本批结论对**当前线上题**成立，而不是对某个历史快照成立。

#### 13.12.1 这里踩到一个必须记下来的错：哈希不同源导致 35/35 误报

第一次做这项核对时，SQL 写的是 `ui_schema::text`，得到的是 Postgres 自己的
排版字符串；而冻结侧 `freeze_batch7.py::_sha()` 吃的是 jsonb 被 psycopg
解析后的 **dict**，做 canonical JSON 再 sha256。两边不是同一份输入，于是：

```
UI drift 088d0469 | live sha f6d499ec8bea vs frozen 28a71baf3f08
... （35 题全部如此）
answer drift=0  stem drift=0  ui drift=35
```

现象是「全部 35 题 UI 契约都被改过」，看起来像一次严重的线上篡改。实际是
**核验脚本自己算错了**。改成同取 dict + 同款 canonical 函数后 drift=0。

这正是 13.9 记过的那条：**验证脚本自身出错会产假结论**。今天第二次踩到。

#### 13.12.2 修法不只是"改回对的那一列"

只把 `::text` 去掉，仍然是「两个文件各写一份哈希函数、靠人眼保证一致」。
所以做了三件事：

1. `q03_batch7.py` 新增 `_canon_sha256()`，注释里点名它**必须与
   `freeze_batch7.py::_sha()` 逐字同款**，并写明换掉任一参数会让 35 题全部误报；
2. `main()` 的漂移检查从 1 列扩到 3 列（答案 / 题干 / UI 契约），任一项不符
   即 rc=2 并分列点名。**只核答案**的话，题面被改这种情形查不出来；
3. selftest 增加判据 G：把两个文件里的哈希函数在同一批真实对象上逐题比对，
   并额外核「清单里存的 sha 能否由清单内容重算出来」——防**清单哈希是编的**
   （那种清单永远自洽，与文件自洽一样结构上查不出）。

判据 G 的两条变异都验过，且都点名到具体题目：

| 变异 | 结果 |
|---|---|
| `_canon_sha256` 去掉 `separators`（改用 json 默认带空格） | rc=1，**35/35** 报「核验侧与冻结侧哈希函数不一致」 |
| 只改清单第 1 题的 `stem_sha256`，内容不动 | rc=1，点名 `088d0469: 清单里的 sha256 与清单内容重算不符（哈希是编的）` |

第一条尤其值得留档：它复现的正是当天真实发生过的错法。若没有这条自证，
下次有人「顺手」把 separators 去掉，drift 检查会 35/35 报错，而没人知道
错的是核验器。

### 13.13 复核指出的两处错误与整改（2026-10-26 晚）

第七批报告提交后经复核，指出两处实质问题。两处都经脚本独立重算确认为真，
不是口径差异。

#### 13.13.1 第一处：进度账漏扣 8 道 `Q03_only`

| 指标 | 原报告 | 复核重算 | 裁定 |
|---|---:|---:|---|
| Q03 累计已审 | 150 | 150 | 一致 |
| Q03 尚未审 | 62 | 62 | 一致 |
| `both` 尚未审 | 55 | 55 | 一致 |
| **`Q03_only` 尚未审** | **15** | **7** | **原报告错** |
| `Q05_only` 总量 | 12 | 12 | 一致 |

**根因**：七批累计 150 题里，第七批 35 题是 **27 both + 8 Q03_only**。
而此前 `both 待核` 的算法一直写 `both 总数 − 完成总数`，隐含前提是
「全部完成题都来自 both」——这个前提在前六批 115 题成立，第七批破了。

```
第七批构成：27 both + 8 Q03_only
  Q03_only 原 15 道 − 已做 8 道 = 剩 7 道
  验算：55 + 7 = 62   ✓
```

**为什么危险**：两处错在 **Q03 总数上互相抵消**（62 始终对），所以只核
总数永远发现不了。这是「两个不同分母不能强行相等」的同类形态——
**同一分母下的分类，不能靠总数验证。**

**整改**（不止改数字）：

1. `check_progress.py` 新增归属分解，三类分别入账后逐项打印，
   不再给单条减法；
2. 新增三条声明：`EXPECTED_DONE_BOTH=142`、`EXPECTED_DONE_Q03_ONLY=8`、
   `EXPECTED_TODO_Q03_ONLY=7`，与实际不符即 rc=1；
3. 新增恒等式判据 `both 待核 + Q03_only 待核 == Q03 待核`（即 `55+7=62`），
   写成判据而不是文档注释；
4. 新增归属分解闭合判据 `both + Q03_only + Q05_only == 完成总数`。

**回归负例（用户明确要求）**：P7a 与 P7b 两条，各自单点注入真实错值——

| 变异 | 结果 |
|---|---|
| P7a `EXPECTED_TODO_Q03_ONLY` 声明成 15（原错误值） | rc=1，点名「Q03_only 待核验: 实测 7，文档声明 15」 |
| P7b `EXPECTED_TODO_BOTH` 声明成 47（`197−150` 的字面结果） | rc=1，点名「both 待核验: 实测 55，文档声明 47」 |

**P7 的第一版是无效变异，已重写**。第一版用「从第七批删 1 道 Q03_only、
再从待核池补 1 道 both」构造，想测「总数仍 62 但分类错」。三个问题：

- 它同时打断了族统计、verdict 统计、并集一致性等若干判据，rc=1 了但
  **说不清是哪条判据抓到的**；
- 断言只查 `"both 已完成" in out`——而这两个词在**正常输出里也恒存在**，
  是恒真式；
- 反向验证（停用归属判据）时它**仍然 PASS**，直接暴露了这一点。

改成单点改声明 + 断言具体失败行后，反向验证 PASS→FAIL 正常翻转：
停用 `Q03_only 待核` 判据 → `P7a` 报 FAIL（7/8）；停用三条归属判据 →
同样 FAIL。**这是本轮第三次「变异无效 ≠ 检测器失效」。**

#### 13.13.2 第二处：150 题「已审查」不等于 150 题「独立验证通过」

第七批 35 题里有 3 题不是独立 MATCH：

| 第七批结论 | 题数 | 能否算独立答案验证 |
|---|---:|---|
| `MATCH` | 32 | 可以 |
| `STEM_GIVEN_ANSWER_AGREES` | 2 | 不可以，只证明与题面直给值一致 |
| `UNVERIFIABLE_FROM_STEM` | 1 | 不可以，题干缺少必要事实 |

#### 13.13.6 第二轮复核发现的 P6 状态栏漏洞（2026-10-27）

复核方在隔离目录复现了一个**真实的门禁漏洞**，并给了最小修复补丁。这一处
不是文档措辞问题，而是代码里的「覆盖完成」状态仍可能被错误触发。

**漏洞本体**：`cleared` 用人工声明 `EXPECTED_FAMILY_TOTAL` 当分母。

```
cleared = sorted(f for f, t in EXPECTED_FAMILY_TOTAL.items()
                 if t > 0 and fam_done.get(f, 0) == t)
```

**根本问题不是算错，而是「被测对象同时充当判据的分母」**：声明表本来是要被
核对的东西，却决定了「什么算完成」。把构造族完成数减到 53、同时把声明总数
也改成 53，`fam_done == t` 成立 → 该族进「覆盖完成」栏，而实际全族仍有 54 题。

**更关键的是判据也问错了问题**：P6 只查输出里有没有 `53/54`，没查它出现在
哪个状态栏。而 `未覆盖完成` 那行同样会印 `53/54`，于是错误实现照样命中、
仍然 PASS。**「判据问错了问题」和「实现有 bug」是两件事，必须分别修**。

**三层修复**（缺一可绕）：

| 层 | 修法 | 反证（注入错误后必须 FAIL） |
|---|---|---|
| 实现 | `cleared` / `not_cleared` 一律取实测 `fam_total` | 注入「声明分母」→ **8/9 FAIL、rc=1** |
| 判据 | P6 定向断言：`53/54` **在**「未覆盖完成」栏、**不在**「覆盖完成」栏、且不得出现 `53/53` | 同上，点名「未完成被标成覆盖完成」 |
| 补漏 | **P6b**：未在声明表登记的族仍须出现在缺口栏 | 注入「缺口枚举取声明表」→ **9/10 FAIL、rc=1** |

第三层是本轮自查追加的：只修 `cleared` 时，`not_cleared` 退回声明表仍能
PASS（实测 9/9 通过），因为声明齐全时两栏结果相同。反证：声明表缺该族时，
缺口会**整栏消失**——数字全对、rc 仍 0，却少报一族未完成。

**顺带发现同一根因的另一面**：`not_cleared` 取实测全集、`cleared` 取声明
分母时，同一族会**同时出现在两栏**，并印出「未覆盖完成 … 尚余 0 题」这种
自相矛盾的行。已加两条自检：两栏交集必须为空、缺口栏不得显示「尚余 0 题」。

**当前 150 题的正确进度数字不受影响**：150 已审查 / 147 独立 MATCH /
3 特殊结论 / 62 待核 / `both 142 + Q03_only 8` 全部未变。修复只改变了
「状态如何判定」，没有改变任何计数。

#### 13.13.7 终态回归 P9：判据必须能在「全部做完」那天为真

P6 整改后的第二步（两侧都改取实测 `fam_total`）仍未收口，且在**当前 150 题
的状态下完全看不出来**。复核方用合成终态把剩余 62 题临时标为已审，原实现

实测 `git rev-list --count main..feat/FE-1472-batch7-q03` = **9**，

**错因值得记下**：我逐段核对了「每段是否相等」，五段全 ✓，就写了「8 个提交
全部覆盖」——**每段都对 ≠ 总计对**。这正是本项目反复记的同一类错型（只核

**⚠️ 上表已过期，且它永远会过期——所以不要再往里追写数字。**

上表是 `5d789b7` 时点（整链 9 / #135 区间 2）的记录。补 P9 后变成 10（区间 3），
再补一次文档更正又变成 11（区间 4）——**每提交一次，这个数字自己就失效一次**。

所以这里不再写当前值，改写**不变量**——它们在任何时点都成立，可随时复核：

| 不变量 | 判据 |
|---|---|
| 整链提交数 = 唯一 SHA 数 | `rev-list --count main..X` == `rev-list main..X \| sort -u \| wc -l` |
| 逐段之和 = 整链总数 | `Σ(相邻区间差)` == `rev-list --count main..X` |
| `#135` 区间 = 整链 − `#136` 累计 | `count(d2..b7)` == `count(main..b7) − count(main..d2)` |
| 区间首尾相接、无遗漏 | 每个分支都是下一个的祖先（`--is-ancestor`） |

**「逐段相加 = 总数」这一条才是当初真正抓出错误的判据**：8 和 9 的差别不在
任何一段，而在合计。写固定值只能证明「某一刻数过」，写不变量才能在任何时刻
**重新验一遍**——这正是「不能由脚本重现的结论只是人工快照」那条的适用。

四条不变量已固化成脚本 `scripts/iqc/rt1472/check_pr_chain.py`，并接进门禁
**第 25 项**（`check_pr_chain` + `--selftest` 各一行）。需要当前值时现场跑，
不要引用本文：

```bash

```

写成脚本后，当场又抓到两个**人工核对根本看不见**的问题：

**一、「逐段和 == 总数」会白送通过（段长为负）**

累计差分假定「scope 逐级增大」。造一个断裂图（`#134` 与 `#136` 之间断链）
实测：

```
逐段   {'#132': 1, '#133': 0, '#134': 1, '#136': -1, '#135': 2}
逐段之和  3          整链提交数  3      ← 相等！
祖先关系  #134 ⊂ #136 ✗
```

`#136` 段算出 **−1**，把多出来的部分削平，`1+0+1−1+2 = 3` 恰好等于整链 3。
**「逐段和 == 总数」照样成立**，只有祖先关系那一条在报警。

> 这是本轮第二次遇到「判据自己给自己找平」：上次是「两栏都调同一个函数」，
> 这次是「负数把差额抵消」。**只要有抵消的可能，恒等式就不是证据**。
> 故单独加判据：段长为负即失败（自证 M5）。

**二、失败明细写进 stderr 等于没写**

第一版把失败明细打给 `stderr`。实测在断裂图上 rc=1，但 `2>&1 | tail` 之后
**一条明细都看不到**，只剩「整链覆盖不成立」一行。CI 里读日志的人只看最后
几行——**写进被截掉的那条流，等于没写**。已改走 stdout。

这与 §13.13.11 三中 `pr_gate` 的同一毛病是同一个根因：**失败不可诊断，
与不失败同效**。两处现在都要求在结论之后紧跟明细，且与结论同流输出。

**自证**（5/5，含一条反向对照）：

| 构造 | 期望 |
|---|---|
| 基线（1/2/1/3/2、整链 9） | 不报错 |
| M1 整链数 9 ≠ 唯一 SHA 8 | 检出 |
| M2 **逐段 1+2+1+3+2=9 但声明 8** | 检出（分项全对、合计错） |
| M3 `#135` 区间 3 ≠ 整链10 − `#136`累计6=4 | 检出 |

M1/M2/M3/M5 会全部"检出"，自证等于没测。

**三、无 `.git` 环境下的两种假象（复核方最容易踩到）**

把提交导出成 `git archive` 的 tar 再跑门禁，暴露两个问题。**复核方拿到的
很可能就是这样一份拷贝**，所以不是理论问题：

| 现象 | 为什么是错的 | 修法 |
|---|---|---|
| `check_pr_chain` 返回 rc=2，门禁当普通 FAIL | 不是「链覆盖不成立」，是「这项工作在这里做不了」。混淆后读者会以为链断了 | rc=2 仍判失败（不静默算 PASS），但明细写明「环境问题（无 git 仓库）」 |
| 紧接着又报「门禁行数不一致」 | 环境失败少 1 行，**行数必然偏少**。两条 FAIL 并列，看起来最像问题的是文档数字，而真正要处理的是环境 | 只在无其它失败时才核对行数；否则明说「跳过核对」并说明原因 |

第二条尤其要记：**假失败会盖住真失败**。读到两条 FAIL 的人会先改文档，
改完仍红，才会回来找环境——多绕一圈。故跳过分支也不再打印第二行实测值，
否则会出现「跳过核对」与「文档不一致」并列的自相矛盾输出。

双向验证（都必须正确，缺一不成）：

#### 13.13.11 第三轮收尾：三处"数字没有实测来源"（2026-10-27）

本轮补 P9 时，顺带发现**同一类病还有三处**。它们的共同点不是算错，而是
**那个数字没有任何东西在核它**——写对写错都无人报警。这三处已全部改成
实测，并且每处都配了反证。

**一、`BATCH7 9/9` 接错了脚本（D7 自证检出数）**

D7 的职责是「文档里那行自证计数必须等于各脚本实跑的分子分母」。第一版把
`BATCH7` 接到了 `q03_batch7.py`，而那个脚本的输出形态是

```
Q03-BATCH7-SELFTEST: PASS（答案篡改 32/32；题干数字变异 16/16 模板；…）
```

**没有** `（N/N 检出）` 这一形态，于是 D7 取不到分母、直接 FAIL。文档里那个
`BATCH7 9/9` 真正来自 `check_batch7_ledger.py`（账实核**区分力**自证）。
两个脚本名都带 batch7，接错了照样"看起来对"。

> **判据接错源，与文档写错数字是同一种病**，只是错在判据这一侧。
> 而且判据接错更难发现——它不会让数字变，只会让判据静默失效。

**二、D7 首版把分母回填成分子（恒真式）**

首版写的是：

```python
_d7_parts.append(f"{_label} {_r[1]}/{_r[1]}")   # 分母/分母
```

自证真跑出 6/7 时，文档照写 `6/6` 仍然 PASS——因为判据比的是「分母等于
分母」。这是本项目已记的恒真式变体的第四种：**①自己比自己 ②词恒存在
③同一函数两边各调一次 ④分母回填成分子**。

改成取 `_r[0]`（实测检出数）后，另加一条独立断言：**任何一项自证若真跑出
未全过，文档一律不得记成 N/N 全过**。

反证（四种，全部实测）：

| 构造 | 结果 |
|---|---|
| 文档写 `PROGRESS 10/11`（分子错） | rc=1，2 条 ✗ |
| 文档写 `PROGRESS 11/12`（分母错） | rc=1，2 条 ✗ |
| 文档写 `BATCH7 16/16`（用错脚本口径） | rc=1，2 条 ✗ |
| 文档写 `BATCH7 9/90`（尾部追加数字） | rc=1，1 条 ✗ |
| `INDEPENDENCE` 改成真跑出 `6/7`，文档照抄 `6/7` | rc=1，**仍 FAIL** |

最后一条是关键：**照抄实测错值也过不了**。原文若只做"文档 == 实测"这一个
比对，照抄错值就会被放行——「一致」不等于「正确」。

**三、`门禁 24/24（32 行 PASS）` —— 行数写错了 1**

上一轮汇报与交接记录都写「门禁 24/24（**32 行 PASS**）」。实测：

```
$ python scripts/iqc/pr_gate.py | grep -c '^PASS'
31
```

`32` 是错的，**且它骗过了所有已有判据**：门禁自己只报 `24/24 PASS`（说的是
**项数**，不是行数），`check_doc_claims` 核的是别的数字。**两个都写着 PASS
的不同量，最容易被当成同一个数**——这正是本项目记的「总数正确、分类错误」
换了个壳。

`24 项 → 31 行`的分解也核对过（不是巧合）：

| 一项打多行的位置 | 行数 |
|---|---|
| 第 3 项「覆盖矩阵一致性」 | 3（未知 renderer / 枚举合法 / 快照一致） |
| 第五批 | 2（账实核 + 自证） |
| 第六批 | 2（账实核 + 自证） |
| 第七批核验器 | 2（`--selftest` + `--crossbatch`） |
| 第七批账实核 | 2（账实核 + 自证） |
| 第 24 项「文档数字」 | 2（audit + 自证） |
| **24 + 7** | **31** |

修法上踩了三次坑，都值得留档：

- **① 判据不能算进自己**。第一版用 `note()` 打「门禁行数」这一项，于是
  检查自己占了一行：行数由 31 变 32，判据立刻自相矛盾；若顺手把文档改成
  32，下次加任何一项又要改文档——**数字随判据漂移**。改用 `info()`
  打印但不计入行数，失败仍走 `fails` 硬 FAIL。
- **② 计数主体自己数，不能循环**。先试过让 `check_doc_claims` 反向调
  `pr_gate`，变成 `pr_gate → check_doc_claims → pr_gate`，实测 SIGTERM 137
  挂死。行数是 `pr_gate` 自己打印的，就由它收尾时自数。
- **③ 审计之后不许再 `note()`**。反证第一次**无效**：把模拟项插在审计
  *之后*，总行数由 31 变 32、判据却仍报「一致」、rc=0——因为那份行数
  在插入前就数完了。这不是靠"记得把审计放最后"能防的，故加**封口**：
  审计跑过即置 `_sealed`，之后再 `note()` 直接判失败。

另外两项也改成实测，不再手写：

- **项数**：取头部编号清单（`NN.` 开头）的行数，不写死 24。反证：往清单
  加一条 `25.` → rc=1。
- **解析下限**：清单格式若被改（如 `1.` 改成 `1)`），`_n_items` 会静默变 0，
  而文档若也写 0 项就"一致"了——**解析失配冒充正确结论**。故 `_n_items < 10`
  直接失败。反证：把头部编号全改成 `1)` → rc=1、FAIL(2)。
- **不留开关**：首版有 `--no-row-audit`，等于给「跳过行数对账」留了正式入口。
  **凡是能被参数关掉的判据，出错时第一个被关掉**。已删除。

**顺带修掉一处更基础的缺陷**：`pr_gate.py` 收尾只印 `PR-IQC-GATE: FAIL (n)`，
**不打印任何失败原因**——因 `note()` 失败会印一行，但收尾对账是直接
`fails.append(...)`，不会印。实测 `FAIL (2)` 而两条原因一条都看不到。
这与「报错吞掉判据 = 空转」是同一边的：**失败不可诊断，与不失败同效**。
现已在结论之后输出明细（放在结论*之前*会被后面几十行 PASS 冲散）。
