### 3.1 8 道 `estimation-canvas`：**两笔账必须分开**——标准答案核验 vs 评分容差核验

上一版这里写了两句话，复审都推翻了：

- 写「核验方式是『存储值 ∈ 可接受集合』，**不是**『存储值 == 独立算出值』」→ **推得过远**；
- 用 `|actual − target| ≤ 6` 当作一致性证据 → **这个不等式不能代替标准答案核验**。

8 道全部是「以 10 个为一组估一估，把滑条移到最接近的整十数」，配置形如
`{"max":60,"min":0,"actual":N,"target":T,"expected":T,"reference":10,"tolerance":6}`。

**第一笔账：标准答案核验（内容问题）**

标准答案是**由 `actual` 唯一确定**的，不是「一个容差区间」：

```
目标值 = round(actual / 10) * 10      # 最近整十
```

这不是我编的规则，是 renderer 自己的配置守卫（`estimationCanvasV2.ts:62`
`Math.round(actual/10)*10 !== expected → 拒绝解析`）。实测 8/8 一致：

| rvid | actual | 最近整十（=标准答案） | target / answer | 一致 |
|---|---:|---:|---:|---|
| 13c3b756 | 18 | 20 | 20 | ✓ |
| 46b80862 | 47 | 50 | 50 | ✓ |
| 48817fba | 31 | 30 | 30 | ✓ |
| 49cd865c | 38 | 40 | 40 | ✓ |
| b0b699be | 46 | 50 | 50 | ✓ |
| b7282785 | 54 | 50 | 50 | ✓ |
| b77322ff | 49 | 50 | 50 | ✓ |
| bb306616 | 32 | 30 | 30 | ✓ |

**第二笔账：评分容差（评分契约问题）**

`tolerance=6` 在代码里**不是用来判对错的**：

- `evaluateEstimation` 只有 `e === config.expected` 才 PASS（严格相等）；
- `tolerance` 只出现在 FAIL 分支的 `close` 字段里——
  用来区分「差一点点」和「差很多」，是**教学反馈粒度**，不是判分；
- 后端 `_judge` 是 `float(expected) == float(user_answer)`，也是严格相等。

所以「容差」在本项目里**不构成可接受集合**。上一版把它写成「按容差判定」
与代码不符，已撤回。

**为什么 `|actual − answer| ≤ 6` 不能当证据**（复审给的例子，已复算）：

| rvid | actual | 标准答案 | 容差 6 以内的整十 |
|---|---:|---:|---|
| b0b699be | 46 | 50 | **40 和 50 都在内** |
| b7282785 | 54 | 50 | **50 和 60 都在内** |

以 46 为例：最近整十是 50；40 与 46 相差 6，也落在容差带里，但 40 **不是最接近的整十**。
所以 `|actual − answer| ≤ 6` 对 40 和 50 同样成立，它**无法把正确答案与容差内的错误答案分开**。
`actual` 与 `answer` 数值不同（46≠50）也不是独立性的证明——两者本来就该不同。

**净结论**：8 道的**标准答案**核验通过（`round(actual/10)*10 == answer`，8/8）；
**评分容差**的语义是「反馈粒度」而非「判分区间」，且「容差围绕 `actual` 还是围绕目标值」
这一问在当前代码里有明确答案（围绕 `expected`，见 `evaluateEstimation.close`），
**但没有任何一处把它当作判分依据**。第 9 条 `cd7f008d` 是 `task_type=estimation`（R1，开放估算族），
配置同型，另需看「是否说明依据」，本表不含它。

**适用范围（复审已两次收紧，这里是最终口径）**

先说清这一列证明了什么、没证明什么：

| 已证明 | **未**证明 |
|---|---|
| 按 `kind` 精确匹配得到的计数，与存储值一致（9/9 + 1/1） | 「长方形」这个数学概念的边界与 `kind=="rectangle"` 等价 |
| `target_kind` 与题面用词一致（长方形题 `target_kind=rectangle`） | 该学段应该如何界定「正方形是不是长方形」 |

复审给出的两条修正，都已落实：

1. **「按中学口径应为 2」是我算错的，应为 3。** 两题配置完全相同
   （`square×2 / rectangle×1 / triangle×2 / circle×1`，六张卡），
   若把正方形纳入长方形，计数是 `1 + 2 = 3`，不是 2。
2. **「附件没有提供足以支持这一学段划分的依据」**——所以我不能靠「小学教材口径」
   这个假设来消除约定问题。`kind=="rectangle"` 是**软件类别精确匹配规则**，
   它和「长方形的完整数学定义」不是一回事；把前者当作后者的实现，
   是把工程枚举当成数学分类学。

因此这两题的结论只能记录为：

> **按配置枚举标签 `kind` 精确匹配，计数与存储值一致；数学分类约定仍需确认。**

而不是「配置一致 → 题意无歧义」。**配置一致不等于题意无歧义**：
配置能保证「我们数的是哪一类标签」，保证不了「这一类在数学上含不含正方形」。

> **口径澄清（第三批复审后补写，消除本报告内部矛盾）：**
> 上表「9 条 shape-gallery 逐题核实」只针对**答案类型与计数一致性**——
> 即「题面问的是数量、按 `kind` 精确匹配数出来的数 == 存储值」。
> 它**不是**「9 条 shape-gallery 的题意已全部核完」。
> 子集约定（长方形含不含正方形）这**一个**未决问题确实覆盖全部 9 条，
> 所以只要它未决，9 条的题意就都还挂着一个限定条件。
> 两句话说的是一件事的两面，不矛盾：
> **计数一致已核（9/9），数学分类约定未决（9/9 共享）。**
> 后续报告里不许再写「shape-gallery 已全部核完」这种省略限定语的表述。

## 四、判据校准记录（含四次失败）

分族是启发式，错判**不会报错**，只会静默改变结果。所以本轮把每次校准都做成定点回归测试，并把失败写进注释。

### 失败一：动词表漏词，25 条构造题被判成数值题

首版动词表只有 `摆/放/组成/凑/排列/延拓/拼/画`，漏掉真实题面用词：

```
stem: 桌上有4张数字卡…请拖动卡片，把它们按数字从小到大排好，再提交完整顺序。 → answer 1469
stem: 颜色编码规律板的前四格依次是 4、2、4、2…再按顺序补上接下来的两格。 → answer 42
```

后果：`construct_constraint` 首版只有 **38** 条。补 `排好/排序/从小到大/从大到小/补上/接着/下一格/拖动/改填` 后升到 **53**；后续修正两处判据（删 R4、补 `续排`）后最终为 **54**。三次数字分别对应三个不同版本的判据，不可混用。

### 失败二：`×` 被当成判断词，「5×5方格盘」被判成判断题

```
stem: 在5×5方格盘中…棋子从(2,2)出发，要到(0,1)…到达后提交终点格编码。 → answer 1
```

`×` 命中了「5×5」的乘号，该题答案 `1` 是格编码，与真假无关。修正为：符号类 marker（`√`/`×`）歧义过大，一律不参与判定；判断词改用语义词（`判断/检查/是否正确/正确填1/错误填0`）。

### 失败三：`DRAG_RENDERERS` 是死代码，判据被伪装成「含交互形态」

首版定义了 `DRAG_RENDERERS` 常量却**从未参与任何判定**，而文档里却写着「交互形态旁证」。读者会以为交互形态是判据的一部分，实际是装饰。已删除，并在测试 T12 里锁住「不得再出现该常量」。

### 失败四（自伤）：R4 与 R3 冗余兜底，导致判据无法被变异验证

R4（「题面要求提交顺序/补位」）的关键词含 `补上`，与 R3 的构造动词表重叠。后果：把 `补上` 从动词表删掉，T13 仍然 PASS——因为被 R4 接住了。**两条规则互相兜底，等于每条都无法被单独检验。**

处理：删除 R4。但删除后做了逐条比对，发现**有 1 条题真的漂移了**：

```
rvid 82ff6618  pattern-board
stem: 小贝观察颜色编码3、5、3、5后说："接下来的两格都应填5、5。"…若有错误，在规律板中填入你验证出的正确两格…
answer: '35'
```

它的题面用「续排 / 填入」，不含任何原动词。补 `续排` 进动词表后修回。

**这里我犯过一个错并已修正**：删除 R4 后的第一版注释我写了「删掉 R4 后 224 条逐条一致」，那是我凭印象写的、**未经核对且是错的**。逐条比对才发现有 1 条漂移。现已把注释改为实测结论，并把这条教训写进代码。

同时确认 `填` 字**不能**直接加进动词表：会误拉 6 条 `□+8=17 请把数字卡填入空格` 的纯算术题进构造族。同类词面、不同交互语义，只能靠更具体的词区分。

**注意这里不是「方向相反」**：四条路径都是「按题意与约束求出数学对象 → 按提交契约编码 → 比较答案」，差别只在**求出的对象类型**（标量 / 序列 / 排列 / 构造）。我上一轮把 `money` 与 `sorting` 说成「方向相反」是错的，复审已纠正。

所以 **Q03 不能一律「照 answer 反推」**。`geometry_constraint` 尤其要注意：多解题的答案只取某个规范量（这里是面积），核验时必须先确认「题面问的是这个规范量」，否则会把「合法构造存在」错判成「该构造唯一」。

### 局限二：答案形态无法区分求解路径（实测失败）

曾试图用「题面是否要求提交顺序」判断答案「是摆出来的还是算出来的」，实测不可靠：

- `direction-grid`「要移动几步」答 4 —— 被判成 assembled，其实是数出来的
- `place-value`「组成 352」答 352 —— 被判成 computed，其实是拼出来的

结论：`answer_shape` 只作**旁证**，不参与判族、也不参与定求解路径。代码里已写明这一点，避免后人误用。

### 局限三：值域同构而语义不同 —— 答案类型已核实，**0 条因值域转人工**

上一版把 5 条写成「需人工确认」，复审指出方向不对：「需要区分的首先是**答案类型**，而不是数学题本身出现了歧义」。本轮已按答案类型逐条核实（第三节 3.2），**10 条答案类型全部一致、0 条因「值域是 0/1」而转人工**。

## 六、语义族与 Q03 核验链的对接

用户 §三 规定的核验链：**题干与必要配置 → 独立求解／合法解集合 → 与现有答案比较 → 留存推导与适用边界**，且「数据库 `answer` 可以作为比较对象，不能反过来参与生成预期答案」。

按求解路径落地（比按族落地更贴近实际操作）：

| 求解路径 | 数 | Q03 做法 |
|---|---:|---|
| `numeric_exact` | 170 | 从题干重建算式/数量关系 → 独立计算 → 与 `answer` 比标量相等。判断题额外核验「0/1 映射方向」与题面真假是否一致 |
| `numeric_tolerance` | 9 | 先由 `reference`+取整规则算出**唯一标准答案**（最近整十）→ 与 `answer` 比等式。**不是**「落在可接受集合内」——见 §3.1 |
| `sequence_order` | 18 | 枚举合法序列/相位 → 定规范序（如升序唯一）→ 按契约编码 → 比对 |
| `digit_config` | 9 | 位值+卡片使用约束 → 求合法排列 → 比对 |
| `geometry_constraint` | 9 | 枚举合法构造（可能多解）→ 确认题面问的是哪个规范量 → 比对 |
| `count_by_attribute` | 9 | 从配置枚举对象 → 按属性精确匹配计数 → 比对 |

**首批建议**：先做 `numeric_judge ∩ both` 中 `solve_path=numeric_exact` 的题（约 142 条），单题同时产出 Q03 结论与 Q05 候选，避免两条线各跑一遍。
