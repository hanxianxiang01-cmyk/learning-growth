## 5. 本轮修复的缺陷

### 5.1 CORS 白名单缺 3102（阻断级）

- **症状**：浏览器打开 3102，页面显示 `Failed to fetch`；后端日志只有 `OPTIONS /v1/guest/bootstrap → 400`。
- **根因**：`cors_origins` 只有 3000/3100/3101。预检被 Starlette 直接拒，真实 POST 从未发出。
- **修法**：`apps/learning-api/app/core/config.py` 补 3102（localhost 与 127.0.0.1 两条）。

### 5.2 StrictMode 双挂载造孤儿游客（数据污染）

- **症状**：屏幕完全正常，但 `guest_identity` 行数成对增长，同一对时间戳只差 10–60 ms。
- **根因**：dev 环境 React StrictMode 双挂载，第二次 effect 在第一次的 Set-Cookie 到达前发出 bootstrap，服务端认不出是同一个人 → 每次开页多造一个游客。
- **判据**：开一次页，`bootstrap` 请求数必须为 1、游客数必须恰好 +1。修复前实测 +2。
- **修法**：模块级 in-flight Promise `bootstrapOnce()`，失败时清空缓存以便重试（避免网络抖动一次就永久锁死会话）；主分支与 V6 同步修。

### 5.3 429 业务码解包缺失（儿童能看到的错误是错的）

- **症状**：撞每日上限时孩子看到「这一步暂时没有完成」，而不是「今天已经完成 30 道题啦」。
- **根因**：后端 429 响应体是 `{"detail": {"code": "LE-4291", "message": ...}}`，前端只读 `body.code` / `body.message` → 恒 `undefined`，`humanizeError` 里 `LE-4291` 分支永远不命中。**注释/契约承诺了，代码没做**。
- **修法**：`http.ts` 解包 `detail`（`body.code ?? inner?.code`）。
- **反证**：stub fetch 返回 429 → 断言 `code === "LE-4291"`，修复后 PASS；变异回旧写法 → `code = undefined` 精准红；还原后 sha `b32d14c6…` 逐字节一致并复跑 PASS。

### 5.4 `--accent` 从未定义 → legacy 主按钮恒青绿（皮肤失效的真因）

- **症状**：蓝色皮肤页面上，主按钮是青绿色。这正是「皮肤呢？你确定是这一版吗」被问的那一处的真因。
- **根因**：`globals.css` 靠后的一条覆盖规则写的是 `.primary-button{background:var(--accent,#2d7a68)}`，而 `--accent` 在**两个分支全仓定义处为 0** → 永远落到硬编码回退 `#2d7a68`。它把前面 `background:var(--cm-primary)` 整条覆盖掉。
- **修法**：把 5 处 `var(--accent,#2d7a68)` 与 2 处 `var(--accent-soft,#e8f4ef)` 改接 `var(--cm-primary,…)` / `var(--cm-primary-soft,…)`。legacy 于是跟皮肤走；V6 模式下 `--cm-primary` 被 `v6Actions.primary (#0a6972)` 覆盖，青绿仍是 V6 的设计，行为不变。
- **反证**：变异改回 `--accent` → 实测按钮色回落 `rgb(45,122,104)`，恰好 2 条判据红（`[3104] 主按钮计算色`、`都不是硬编码色`），未变异的 healing 实例仍全 PASS；还原后 sha `103148be…` 逐字节一致并复跑 12/12 PASS。
- **教训**：`var(--x, fallback)` 里的 `--x` 若从未定义，写着像参与换肤，实际是硬编码。判据不能查「有没有写 var()」，要查**计算色是否随皮肤变化**。

## 8. 这一轮补的是「真实」两个字

前两轮的运行时证据来自 mock 数据源与隔离页面，能证明「界面不崩」，
但证明不了「孩子真能做对一道真题」。本节把数据源换成生产题库，
用**不拦截任何请求**的真实流程重跑，并用两套可复跑判据对账。

### 8.1 方法

| 环节 | 做法 | 为什么必须这样 |
|---|---|---|
| 身份 | 全新浏览器上下文，只通过 UI 进首页 | 拦截或注入 Cookie 就等于绕开被测对象 |

## 9. 合并与 PR（本轮的收尾动作）

### 9.1 先纠正一个错判

上一轮写下「PR 未创建（本机无 `gh`）」，事实是：

| PR | 实际状态（查 API 得知） |
|---|---|
| #87 | `feat/FE-1445-v6-full-migration → main`，**2026-10-14 已建**，DRAFT，`mergeable_state=dirty` |
| #135 | `feat/FE-1472-batch7-q03 → feat/FE-1472-d2-h4-assertions`，已在 Q03 串联 PR 链中 |

**教训**：「本机没有工具 X」不等于「动作 Y 没发生」。没有 `gh` 只是没有命令行入口，
PR 列表是一次 `GET /pulls` 就能读的事实。把「工具缺失」当成「事实缺失」，
产出的是一个看起来有理、但从未被验证的结论。

且这条路差点造成实际损害：把游客模式提交推到 `feat/FE-1472-batch7-q03` 后，
它自动进了 Q03 核验 PR #135（base 是 `d2-h4-assertions`，标题是「第七批 35 题核验」），
diff 从 41 文件涨到 57。发现后已 `--force-with-lease` 回退到 `4988df8`，PR #135 复原。

原因还是那个老问题：**分支名 `feat/FE-1472-batch7-q03` 与它的内容（游客模式）不符**。

### 9.2 main 是受保护分支

`git push origin main` 被仓库规则拒绝（`GH013 Changes must be made through a pull request`）。
规则实测：`required_approving_review_count=0`、`required_status_checks=[governance, child-typecheck, child-build]`、
禁删除、禁非快进。**即：不需要他人批准，但必须走 PR 且三项检查全绿。**

V6 分支只含前端适配，调 `/v1/guest/{bootstrap,heartbeat,me}`，

### 9.7 PR #87 从 10-14 起一直 blocked 的第二个原因：必需检查名被矩阵化打散

合并被拒，返回：

```
Required status check "child-build" is expected.
```

`protect-main` 要求三个精确 context：`governance`、`child-typecheck`、`child-build`。
而本分支把 `child-build` 改成了 `skin: [exploration-lab, healing]` 矩阵，
产生的检查名变成 `child-build (exploration-lab)` / `child-build (healing)` ——
**两条都不等于 `child-build`**，所以永远 blocked。

影响面不止这一个 PR：**一旦合入 main，此后所有 PR 都会卡在同一条**，
因为 main 的 `ci.yml` 也会变成矩阵版。这是个会锁死门禁的改动。

两种修法，选了不改治理配置的那种：

| 方案 | 问题 |
|---|---|
| 改 ruleset，把 required 换成两个矩阵名 | 要动仓库治理配置；且以后再加皮肤就要再改一次 |
| 给矩阵 job 显式 `name: child-build` | 两个实例同名，一红一绿时规则可能被绿的那个满足——**门禁失效** |
| **矩阵 job 更名 `child-build-matrix`，另设汇总 job `child-build`（`needs:`）** | ✅ 采用 |

~~汇总 job 只做一件事：两条皮肤都成功才运行。任一失败 → 它不运行 →
required check 不满足 → 仍然拦得住。**名字回来了，门禁强度没降反升**
（从「构建 1 次」变成「两套皮肤都构建」）。~~

> **⚠️ 上面这段推断是错的，已在 §10.2 用真实 CI 证伪。**
> 下游 job 被 skip 时结论是 `skipped`，**不是 `failure`**，而 skipped 不能可靠
> 阻断合并。当时的实现只写了 `needs:`，等于把门禁建立在一个从未验证过的假设上——
> 而这段文字本身写得像已经验证过。这正是本项目反复出现的「宣称有守卫」形态。
> 修复见 §10.2：`if: always()` + 显式校验 `result == 'success'` + 不满足即 `exit 1`。

结构用 YAML 解析断言钉住：`child-build-matrix.strategy.matrix.skin == [exploration-lab, healing]`、
`child-build.needs == child-build-matrix` 且 `child-build` 自身无 `strategy`。

> 附带一条自己的错：第一次写这条断言时写成 `'matrix' in jobs['child-build']`，
> 断言失败——不是文件错了，是**判据查错了路径**（`matrix` 嵌在 `strategy` 下）。
> 判据自己写错，会同时制造假绿与假红，这已经是本项目第 N 次。

### 10.1 合并后真实 E2E：自建隔离库，全程零写入生产

**为什么不能直接用生产库。** 本机唯一的库凭据 `iqc-database-url` 是 `iqc_readonly`
（实测 `has_table_privilege(iqc_readonly,'guardian','INSERT') = false`）。
`/v1/guest/bootstrap` 要写 `guardian`，被权限拒绝 → 500。500 响应不带 CORS 头，
浏览器把它显示成 `CORS policy` 报错——**上一次就是这样误判成 CORS 配置问题的**。
所以「合并后 E2E 没跑成」从一开始就不是代码缺陷。

**为什么不用本机装 PG 17。** `brew install postgresql@17` 被沙箱拦住
（`sandbox-exec: sandbox_apply: Operation not permitted`）；仓库自带的 `pg_dump`
是 16.2，而服务端是 **17.10**，版本不够不能导出。

**采用的方案（全部只读生产库）**：

1. 用 `pgserver`（pip wheel，自带 PostgreSQL 16.2 二进制）在 `/tmp/pg_e2e` 起一个
   本地实例，端口 **55432**，与生产完全隔离；
2. 从生产库 `pg_catalog` 读取结构，**生成 DDL**（表/列/类型/NOT NULL/默认值、
   主键/唯一/CHECK/外键、非约束索引，约束名沿用生产的真实 `conname`）；
3. `COPY ... TO STDOUT` 逐表导出，`COPY ... FROM STDIN` 灌入本地。

**结构对账（不是"看起来 22 张表就对"）**：

| 维度 | 生产 | 本地 | 差异 |
|---|---|---|---|
| 表 | 22 | 22 | 0 |
| 列签名（名/类型/可空/默认/长度精度） | 193 | 193 | **0** |
| 约束（名字 + 定义） | 83 | 83 | 6 处文本差异 |
| 索引（名字 + 定义） | 46 | 46 | **0** |

那 6 处差异全部是 `pg_get_constraintdef` 在 **PG16 与 PG17 的 pretty-print 不同**：

```
生产(PG17): CHECK (((status)::text = ANY ((ARRAY['running'::character varying, ...])::text[])))
本地(PG16): CHECK (((status)::text = ANY (ARRAY[('running'::character varying)::text, ...])))
```

归一化（取字面量序列 + 去括号/去 `::text` 的骨架）后重新比对：
**83/83 语义等价，0 条不等价**。这一步是必须的——文本不等就宣布"结构一致"
和文本相等就宣布"结构一致"一样不可靠。

**数据对账**：22 张表共 **50122 行**，逐表计数与生产完全一致
（`task_instance` 32762、`learning_session` 5677、`attempt`/`learning_event` 各 3938、
`mastery_evidence` 3133、`resource_version` 304、`resource` 254……）。

**零污染的硬证据**（不是"我打算不写生产"）：

```
pid=83668  python3.1  TCP 127.0.0.1:56324->127.0.0.1:55432 (ESTABLISHED)
pid=83668  python3.1  TCP 127.0.0.1:8000 (LISTEN)
到 RDS :5897 的连接数 = 0
```

后端进程只连本地 55432，**到生产库的连接是 0 条**。整个过程中生产库只被
`SET TRANSACTION READ ONLY` 的会话读过。

### 10.2 CI 聚合门禁：用户的质疑成立，已用真实 CI 做 A/B 实证

上一版 `child-build` 只写了 `needs: child-build-matrix`。用户的判断是对的：
**下游 job 被 skip 时结论是 `skipped`，不是 `failure`，不能可靠阻断合并。**

用同一变异（只让 healing 构建失败、exploration-lab 保持成功）打在两个版本上：

| PR | ci.yml 版本 | `cbm (healing)` | `cbm (exploration-lab)` | **`child-build`（required）** |
|---|---|---|---|---|
| #140（已关闭） | 修复前（只有 `needs:`） | failure | success | **skipped** ❌ |
| #139（已关闭） | 修复后（`always()` + result 校验） | failure | success | **failure** ✅ |
| #138（已合并） | 修复后，无变异 | success | success | success ✅ |

三点结论：

1. 修复前的写法在「一套皮肤失败」时产生的是 **skipped**，用户指出的风险是真实的；
2. 修复后同一变异产生 **failure**，required check 真实失败；
3. 全绿路径仍然 `success`，没有把正常路径判错。

修复内容（不碰仓库治理配置）：

```yaml
child-build:
  needs: child-build-matrix
  if: always()                      # 矩阵失败/取消时本 job 仍执行
  steps:
    - run: |
        result="${{ needs.child-build-matrix.result }}"
        if [ "$result" != "success" ]; then
          echo "::error::双皮肤构建门禁不通过（result=$result）"; exit 1
        fi
```

`failure` / `cancelled` / `skipped` / 空串 全部落进 `!= "success"`，一个都不漏。
门禁强度同时从「构建 1 次」升为「两套皮肤都必须构建成功」。

两个探针 PR 与分支在验证后已关闭并删除，仓库没有留下临时物。

### 10.3 V6 首页补齐「今日剩余 N 题」

**根因**：`MathHomeScreen` 的 `bootstrapOnce()` 拿到整个 guest 对象（含 `quota`），
但只取了 `g.child_id` —— quota 连 state 都没有；`HomeView` 也没有这个参数。
主分支老首页有这条横幅，V6 首页没有，是**移植时漏掉的**，不是视觉回归。

**改法（4 文件 +29/−4，不动首页版式）**：`MathHomeScreen` 增加 `quota` state；
`HomeView` 增参并在 hero 与两栏之间渲染一行提示；`ui-v6.css` 加 `.v6-home-quota`。
文案沿用主分支口径：满额时「今天的 30 道题已经完成啦，明天再来吧」。

**为什么必须加判据 C17**：只断言 API body 里有 `quota` 是**查不出这个缺口的**——
这正是它此前被漏掉的原因。C17 用 **DOM 文本 × API body 双事实源互核**。

实测：`页面="今天还可以练 30 道题" 后端 remaining=30`。

**变异反证**：把文案里的 `quota.remaining` 写死成 `99` → C17 **单独变红**
（19/20，rc=1），其余 19 条全绿；还原后 20/20。判据不是恒真。
