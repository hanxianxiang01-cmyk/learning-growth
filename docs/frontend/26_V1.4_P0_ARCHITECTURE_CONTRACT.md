# V1.4 P0 Architecture Contract

## Contract chain

```text
Renderer Registry
  → Workspace API
  → TaskUISchema
  → Structured Response
  → Diagnosis / Hint Normalizer
  → Frontend boundary
```

## A. Renderer Registry

### Canonical renderer ids

| Renderer | Input contract | Workspace | Response |
|---|---|---|---|
| `number-input` | `kind=number` | none | answer |
| `object-counter` | `visual.type=objects` | object positions | `object-counter` |
| `bar-model` | `visual.type=bar-model` | bar values | `bar-model` |
| `number-line` | `visual.type=number-line` | start/current/jumps | `number-line` |
| `unsupported` | unknown/unsupported | none | safe fallback |

`renderer_id` 是扩展入口。能力节点只负责绑定 renderer 与 capability profile，前端不为每个能力节点复制页面。

未知 `renderer_id` 必须降级到 `unsupported`，不得猜测成已有 renderer。

## B. Workspace API

Workspace 的唯一职责是保存和改变数学表征及受控交互状态：

```ts
state
capabilities
can(capability)
commit(representation, event)
undo()
reset()
applyHint(action)
emitInteraction(type, detail)
```

Workspace 不拥有：

- Mastery 计算
- Diagnosis 决策
- Curriculum 决策
- LLM 调度
- 路由跳转
- 直接答案提交

## C. TaskUISchema

V1.4 新增可选元数据：

```text
renderer_id
interaction_capabilities[]
renderer { renderer_id, version, capability_ids[] }
```

旧 V1.3 payload 仍可以通过 normalizer 运行。

## D. Structured Response

```text
schema_version
answer
representation?
interaction_events[]?
```

`interaction_events` 是审计/学习行为输入，不是 Mastery 计算逻辑。前端只记录发生了什么，不解释“说明了什么能力”。

## E. Diagnosis / Hint

HTTP Adapter 对后端 AttemptResult / HintResponse 做结构归一化。

Diagnosis 继续作为业务载荷处理；`E01~E07` 不进入 HTTP error 处理。

Hint UI Action 只能命中受控 Workspace action：

```text
highlight
align_groups
focus
show_bar_relation
show_number_line_start
```

且在执行前受 renderer capability profile 约束。

## F. P0 acceptance

1. Renderer 选择由 Registry 负责。
2. TaskUISchema 可以声明 renderer/capabilities。
3. Workspace 实际执行 capability gate。
4. Structured Response 可以携带交互轨迹。
5. Attempt / Hint 响应通过 normalizer 进入前端。
6. 未知 renderer 安全降级。
7. V1.3 static QA 保持通过。
