8. 19 Renderer 横向开发缺口
单看 Renderer 容易误判工作量。
实际上 19 个 Renderer 共享大量基础设施，因此不能 19 次重复开发。
P0-01 Renderer Runtime Contract
需要统一：
RendererDefinition
RendererState
RendererProps
RendererAction
RendererEvent
RendererResponse
RendererEvidence
RendererAcceptance
否则每个 Renderer 会自己定义一套接口。
9. P0-02 Semantic Event System
当前最大开发缺口之一。
不能继续使用：
onClick
onChange
onDrag
onDrop
作为业务证据。
需要转换成：
renderer.event
↓
semantic event
↓
evidence
↓
diagnosis
例如：
{
"event_id": "...",
"renderer_id": "number_line",
"event_type": "NUMBER_LINE_MARKER_MOVED",
"task_id": "...",
"attempt_no": 2,
"payload": {
"from": 8,
"to": 12
}
}
这部分直接对应此前确认的 EVT-1208 P0。

19. V1.4 当前真正的开发缺口结论
目前最需要注意的是：
不是
“19 个 Renderer 还要做 19 个页面。”
而是：
4 个已有 Renderer 需要从“组件实现”升级成“完整语义 Renderer”；19 个门控 Renderer 需要在统一 Runtime/Contract 基础上批量完成。
因此当前 V1.4 的开发主线应该正式调整为：
V1.4 Renderer Completion
│
┌────────────┴────────────┐
↓                         ↓
Framework P0                Renderer P0
│                         │
Runtime Contract          19 Semantic
Event Contract            19 Evaluator
Response Contract         19 Evidence
Diagnosis Contract        19 Acceptance
│                         │
└────────────┬────────────┘
↓
Five Vertical Gates
↓
Contract Freeze
↓
Release QA
最关键的判断
现在可以进入开发，但不应该直接让开发人员“把 19 个 Renderer 做完”。
应该先把本矩阵转成：
《V1.4 Renderer Development Task Breakdown》
也就是进一步拆到 FE-14xx → Renderer → 文件/模块 → API → Schema → Event → Evaluator → Evidence → Test Case → DoD 的粒度。
这样开发人员拿到后可以直接执行，而不是再次自行理解这份架构文档。
