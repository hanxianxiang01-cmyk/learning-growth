## 2. 随发脚本的实证缺陷

### P0-A：R3 起点自比较，导致误报和重复计数

上传版在 `for side in ('start','target')` 中，每轮均用当前端点与 start 比较；side=start 时必有 `dr=dc=0`，因此**有效非直线方向题也会产生 FAIL**。构造合法 4×4 网格 `(0,0)→(1,1)` 且 answer=5 的样例，上传版返回“纯直线路线”，为实测误报。

### P0-B：R1 没有禁止包装式答案

上传版仅当 `answer` dict 除 `type/value` **还含其它键**时才判失败，反而将合同禁止的 `{type:'number',value:5}` 当作通过。构造包装式答案样例，上传版返回空错误列表。

### P1-C：R7 “tolerance 不贴边”未实际实现

上传版仅检查 `tolerance >= max`，没有检查 `target - tolerance` 或 `target + tolerance` 是否触及值域边界。样例 max=40、target=2、tolerance=5，上传版仍通过。

### P1-D：受控字段缺失未发现

上传版 `context_family` 只检查**非空且越表**，缺失字段会通过，尽管任务单将受控口径列为前置纪律。该检查可与 Gate 1 Schema 重叠，但不能宣称上传版覆盖了缺失场景。

## 3. 旧包回归与数字口径

- 上传版直接审计原始 `V1.4_P0_Trial_155.json`：`审计 155 题，违规 37 条`，exit code=1。
- **37 是错误消息条数，不是 37 道不同的题**；R3 会重复生成线路错误，因此不能将“37 条”直接作为独立违规数或脚本零误报证据。
- 严格门禁的修订候选对**仍为包装式 answer 的旧 trial155**运行后会产生更多错误消息；它与旧版 37 条不具可比性，不应用新结果篡改原审核结论。
- 历史 Trial-155 属非入库样本。验证候选脚本应以后续 A/B/C v2 合规题包 + Gate 3 parser 金样例交叉校准，而不是把旧包违规计数当作“金标准”。
